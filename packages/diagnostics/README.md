# @apendua.dev/diagnostics

The frame rate readout every headset app in this repo wears. Internal, and not
published.

```
rush build --to @apendua.dev/diagnostics
```

JavaScript with JSDoc types, checked by `tsc` and shipped as source, like
`signal`, `justdom` and `freedom`; the `.d.ts` files under `lib-types` are
generated by `build:types` and are what a consumer sees.

## Why it exists

Every app here already mounted a `stats.js` panel in the corner of the page,
and every one of them mounted it in the one place it cannot be read. The moment
the headset takes the display the page stops being drawn, so the reading that
matters — what the frame rate is _inside the session_, with the panels and the
physics and the soundtrack all running — is the reading nobody can see. The
page's panel measures the desktop preview.

This is the same reading, in the room.

## Using it

Two pieces, the way `@apendua.dev/sound` splits the soundtrack: an object
holding what the readout knows and whether it is shown, made wherever the scene
is built, and a component that measures and draws it.

```js
import { createDiagnostics, Diagnostics } from "@apendua.dev/diagnostics";

const App = component((ctx) => {
  const diagnostics = createDiagnostics();

  return just(new THREE.Scene()).pipe(
    effects(() => {
      use(Diagnostics(ctx, diagnostics));
    }),
    children(/* the game */),
  );
});
```

`use` rather than `children`, because the panel adds itself to the camera — it
is a HUD, and the camera is already in the scene. What comes back from
`Diagnostics` is that camera, exactly as `camera(ctx).pipe(children($(listener)))`
hands back the camera the soundtrack's ears were hung on.

`createDiagnostics()` returns the controls:

|            |                                                                                                    |
| ---------- | -------------------------------------------------------------------------------------------------- |
| `visible`  | Whether the panel is drawn. Starts true; `createDiagnostics({ visible: false })` starts it hidden. |
| `toggle()` | Shows the panel, or hides it. What a button in the app's own panel calls.                          |
| `fps`      | The current reading, twice a second, or null before there is one.                                  |
| `history`  | The chart: thirty two-second averages, oldest first.                                               |
| `ceiling`  | What full height on the chart means, in fps.                                                       |

The last three are there to be read — by a test, by an app that wants the
number somewhere of its own — and are written by the component.

`diagnosticsButton(controls, className)` is the switch, for an app's own panel
to carry:

```js
diagnosticsButton(diagnostics, actionButton);
```

Only the wording and the wiring are shared. The button wears a class name the
app supplies, the way `freedom`'s dropdown and keyboard do, because a panel's
buttons have to look like that panel; `cursor: pointer` is what makes it a ray
target. Pass the controls straight into the panel component alongside the
soundtrack's output picker — a panel that both shows and sets something the
scene owns is the shape the music card already has.

## What it draws

A card about 18 cm across, a metre out, twenty degrees up and to the left of
straight ahead: out of the way of whatever the game has put in front of the
player, and inside the sweep of an eye that has decided to look for it. On it, a
frame rate, and a minute of history as thirty two-second bars. Bars are green
while the display is keeping up, amber where some of the frames are being
missed, red where the scene has become a slideshow — as fractions of the
display's own rate, because 72 fps is perfect on one headset and a quarter of
the frames dropped on another.

The panel is deliberately faint: a third-opaque background, a hairline border,
and no colour it does not need. It is an instrument, not part of the game.

Two things about it are worth knowing.

**It lets rays through.** A head-locked panel sits between the player and
everything else, so an opaque one would be a pane of glass their own pointer
kept landing on. It is projected through a portal with
`{ opaqueToRays: false }`, which is a `@apendua/freedom` option this widget is
the reason for.

**It measures whether or not it is being drawn.** Counting frames is a `+= 1` in
a callback the renderer was making anyway; it is drawing the panel that costs
something, and that is what the switch turns off. A panel switched back on has
the last minute to show rather than an empty chart.

## Keeping it cheap

A performance tool that shows up in its own measurements is worth very little,
so the panel is built to cost as close to nothing as a panel in a portal can.
Its tree is built once and never changes shape. The chart's thirty bars are full
height and squashed with a `transform` rather than given a height each, and
coloured with an inline `backgroundColor` — both the cheap tier described in
`freedom`'s README: a matrix write and a uniform, with no re-measuring of the
panel. Only the reading itself re-rasterizes, twice a second, and it is given a
fixed width so that a two-digit number and a three-digit one put the unit in the
same place.

## What is in it

**`createFrameMeter(options)`** is the arithmetic on its own — no three.js, no
DOM, no signals. It counts against the timestamps the frame callbacks carry
rather than against a wall clock, so a session that stops being drawn reports
the frames it actually got. `chartCeiling(peak)` snaps a reading to the rate the
display is evidently running at (60, 72, 80, 90, 120, 144), which is what the
chart is drawn against. Both are tested in node.
